Yes — that's actually the better strategy.

We should not put every feature into V1. V1 should be the stable production contract containing the core capabilities. V2 can introduce more advanced functionality and breaking API changes.

The key is: don't use V2 merely because V1 has too many endpoints. Versioning should represent a change in the API contract/behavior.

Recommended split for your platform

I'd structure the roadmap like this:

/api/v1/...
    Stable core platform
    Production-critical functionality
    Basic enterprise security

/api/v2/...
    Advanced functionality
    New workflows
    Improved representations
    Features requiring breaking changes

The important distinction

I would think of the versions like this:

                  API
                   │
        ┌──────────┴──────────┐
        │                     │
       V1                    V2
        │                     │
        ↓                     ↓
Stable contracts       Advanced contracts
Production clients     New clients
Mobile/Web              Future clients
Core features           Advanced features


V1 should not mean "old". It should be the first stable contract.

And V2 shouldn't be used simply because you want more endpoints.

For example, if V1 has:

GET /api/v1/exams/{examId}


and you add a completely new endpoint:

GET /api/v1/exams/{examId}/statistics


that generally doesn't require V2. It's additive and can safely be added to V1.

But if you change the response from:

{
  "id": "123",
  "name": "Java Exam"
}


to an incompatible structure such as:

{
  "exam": {
    "identifier": "123",
    "title": "Java Exam"
  }
}


then V2 makes sense.
