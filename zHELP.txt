Cross-service enterprise endpoints

There are also some endpoints that I would standardize across your services.

Health

Every service:

GET /health/live
GET /health/ready
GET /health


For example:

GET /health/live


checks that the process is alive.

GET /health/ready


checks dependencies such as database/cache/message broker.

Standard pagination

For large collections, don't just do:

GET /api/v1/users


with unlimited results.

Use:

GET /api/v1/users?page=1&pageSize=50


and support:

GET /api/v1/users?page=1&pageSize=50&sortBy=createdAt&sortDirection=desc


For enterprise search:

GET /api/v1/users?search=john&status=active&role=student


The same pattern should be used throughout:

/exams
/questions
/attempts
/results
/notifications
/audit-logs
/proctoring/events
/classes

Bulk operations

Enterprise systems benefit enormously from bulk APIs.

For example:

POST /api/v1/users/bulk
POST /api/v1/users/bulk-import
POST /api/v1/users/bulk-delete

POST /api/v1/exams/bulk
POST /api/v1/questions/bulk
POST /api/v1/questions/import
POST /api/v1/questions/export

POST /api/v1/notifications/send-bulk
POST /api/v1/exams/{examId}/candidates/bulk


For very large operations, I'd make these asynchronous jobs instead of keeping an HTTP request open.

Background job API

For enterprise bulk processing, introduce:

POST   /api/v1/jobs
GET    /api/v1/jobs
GET    /api/v1/jobs/{jobId}
POST   /api/v1/jobs/{jobId}/cancel
GET    /api/v1/jobs/{jobId}/status
GET    /api/v1/jobs/{jobId}/result


Then:

POST /api/v1/questions/import


could return:

{
  "jobId": "....",
  "status": "queued"
}


rather than waiting several minutes.

API keys / service-to-service authentication

Because you have multiple services, I would also consider internal service authentication.

POST   /api/v1/service-accounts
GET    /api/v1/service-accounts
GET    /api/v1/service-accounts/{id}
PUT    /api/v1/service-accounts/{id}
DELETE /api/v1/service-accounts/{id}

POST   /api/v1/service-accounts/{id}/rotate-secret
POST   /api/v1/service-accounts/{id}/revoke


However, don't expose these publicly. These should be restricted to trusted infrastructure/admin operations.

For service-to-service calls, I'd prefer strong service identity rather than passing a user's JWT everywhere.

One critical recommendation

Before we start writing hundreds of controllers, we should establish the domain boundaries and ownership.

For example:

AuthService
    owns → Users
    owns → Roles
    owns → Permissions
    owns → Sessions
    owns → RefreshTokens

ExamService
    owns → Exams
    owns → ExamSections
    owns → ExamConfiguration

QuestionBankService
    owns → Questions
    owns → Options
    owns → Topics
    owns → QuestionVersions

ExamAttemptService
    owns → Attempts
    owns → Answers
    owns → AttemptEvents

ResultService
    owns → Results
    owns → Grades
    owns → Certificates

ProctoringService
    owns → ProctoringSessions
    owns → ProctoringEvents
    owns → Evidence

NotificationService
    owns → Notifications
    owns → Templates
    owns → DeliveryRecords

VideoClassesService
    owns → Classes
    owns → Videos
    owns → Sessions
    owns → Attendance

AnalyticsService
    owns → Aggregations
    owns → Reports


No service should directly modify another service's database. Communication should happen through APIs/events/messages.

That is the part that will make the difference between a collection of controllers and an actual enterprise architecture.

My recommendation for your project

Don't implement all ~500 endpoints at once. Build V1 in this order:

1. Shared architecture
2. API versioning
3. Global error/response contract
4. AuthService
5. User/RBAC
6. ExamService
7. QuestionBankService
8. ExamAttemptService
9. ResultService
10. ProctoringService
11. NotificationService
12. VideoClassesService
13. AnalyticsService
14. Jobs/background processing
15. Audit/event infrastructure
16. Gateway/service-to-service security
17. Observability
18. Integration/security tests


That gives you a much safer path to an enterprise-grade online examination/learning platform without creating a giant unmaintainable codebase.
